# C++ 基础语法

这份文档记录当前阶段最常遇到、也最容易混淆的基础语法点。目标不是背概念，而是建立判断标准。

## 1. 声明与定义

本质：

- 声明是在告诉编译器“有这么个名字，它长这样”。
- 定义是在真正提供这个实体或实现。

最小例子：

```cpp
void foo();      // 声明

void foo() {     // 定义
}
```

判断标准：

- 调用一个函数前，编译器必须先看到它的声明。
- 整个程序最终生成可执行文件前，链接器必须能找到它的定义。

常见误区：

- 误以为“别的 `.cpp` 里已经写了定义，这里就能直接调用”。
- 误以为“能通过编译”就代表“最后一定能链接成功”。

自测问题：

1. 如果 `main.cpp` 里在调用前没有看到 `foo();` 的声明，但 `foo.cpp` 里有 `foo` 的定义，报错更可能发生在编译阶段还是链接阶段？
2. 如果当前文件里只有 `void foo();`，但整个工程没有 `foo` 的定义，编译和链接各会怎样？

## 2. 头文件与 `#include`

本质：

- `#include` 不是“建立连接”，而是预处理阶段的文本展开。
- 头文件最常见的作用，是把声明放到当前翻译单元里给编译器看。

最小例子：

```cpp
// foo.h
void foo();
```

```cpp
// main.cpp
#include "foo.h"

int main() {
    foo();
}
```

判断标准：

- 如果头文件里已经有声明，通常不需要在使用处再手写一遍前向声明。
- 真正的关键不是“有没有 include 过某个文件”，而是“调用点之前编译器是否已经看见声明”。

常见误区：

- 把 `#include` 理解成运行时或链接时行为。
- 以为 `.cpp` 文件之间会自动彼此看见内容。

自测问题：

1. `#include "foo.h"` 后，`foo.h` 里已经有 `void foo();`，在当前 `.cpp` 里还需要再声明一次吗？
2. 如果只在另一个 `.cpp` 文件里写了 `foo()` 的定义，但当前文件既没有 `#include` 头文件，也没有前向声明，能直接调用吗？

## 3. 匿名命名空间 `namespace {}`

本质：

- 匿名命名空间用于把函数、变量、类型限制在当前 `.cpp` 文件内部可见。
- 它常用于放“只给本文件使用的辅助函数”。

最小例子：

```cpp
namespace {

void helper() {
}

} // namespace
```

判断标准：

- 同一个 `.cpp` 文件里可以使用 `helper()`。
- 其他 `.cpp` 文件不能直接访问这里的名字。

和 C 的类比：

```cpp
static void helper();
```

在文件作用域下和匿名命名空间的目标接近，但在 C++ 里更常推荐匿名命名空间，因为它也适用于类型和常量。

常见误区：

- 以为它是“模块系统”。
- 以为匿名命名空间里的函数只能在那对大括号内部调用。
- 把它放进头文件，导致每个包含该头文件的源文件都拥有自己的一份实体。

自测问题：

1. 匿名命名空间里的函数，能不能在同一个 `.cpp` 文件后面的普通函数中调用？
2. 为什么匿名命名空间一般更适合写在 `.cpp` 而不是 `.h` 中？

## 4. 读源码时的最小判断顺序

遇到一个函数调用或一个陌生名字时，先按这个顺序想：

1. 这个名字在当前文件里有没有声明或可见定义？
2. 它来自当前命名空间、类作用域，还是别的命名空间？
3. 如果编译能过，它的定义最终会在哪里提供？
4. 这个实体是整个项目公共接口，还是当前文件的内部辅助实现？

当你按这个顺序思考时，很多“为什么这里报错”或“为什么这里要这么写”的问题会清楚很多。
